VOYTEK — AI CONTEXT / CONTEXTO MESTRE DO MVP
Versão: 1.0
Finalidade: fornecer contexto permanente para agentes de IA que trabalham no desenvolvimento da Voytek.

============================================================
1. REGRA DE USO DESTE ARQUIVO
============================================================

Este arquivo é a fonte principal de contexto de produto para o MVP da Voytek.

Antes de criar, alterar, revisar ou sugerir código, arquitetura, banco de dados, endpoints, telas, regras de negócio ou integrações, a IA deve considerar este contexto.

A IA NÃO deve:
- inventar funcionalidades fora do escopo;
- transformar o MVP em uma arquitetura desnecessariamente complexa;
- criar pagamentos bancários reais no MVP;
- permitir que um LLM seja a autoridade final de uma transação;
- confundir saldo lógico da Voytek com dinheiro custodiado pela Voytek;
- adicionar microserviços, Kubernetes, Redis ou mensageria externa sem necessidade concreta;
- criar features futuras como se já fizessem parte do MVP.

Se houver conflito entre uma solicitação posterior explícita do responsável pelo produto e este arquivo, a solicitação posterior pode atualizar o contexto.

============================================================
2. O QUE É A VOYTEK
============================================================

Voytek é uma plataforma de infraestrutura financeira, operacional e de governança para agentes de inteligência artificial.

A ideia central é permitir que empresas deem a agentes de IA:

- objetivos;
- budgets/orçamentos;
- permissões;
- regras;
- níveis de autonomia;
- capacidade de propor ações;
- capacidade controlada de executar ações;
- aprovação humana quando necessária;
- rastreabilidade completa.

A empresa continua controlando dinheiro, acesso, finalidade e responsabilidade.

Resumo conceitual:

VOYTEK = AI + DINHEIRO + EXECUÇÃO + CONTROLE.

Outra forma de resumir:

"Dinheiro programável por objetivo para agentes de IA."

Exemplo:

Uma empresa possui um agente responsável por EPI.

Objetivo:
"Manter estoque suficiente de EPIs para 100 funcionários."

Budget:
R$ 8.000 por mês.

Regras:
- comprar apenas de fornecedores autorizados;
- máximo de R$ 2.000 por compra sem aprovação;
- compras acima de R$ 2.000 exigem aprovação humana;
- não ultrapassar o budget mensal;
- somente categoria EPI;
- agente precisa estar ativo.

O agente pode identificar uma necessidade e propor uma compra.

A Voytek verifica as regras antes de permitir qualquer ação.

============================================================
3. PROBLEMA QUE A VOYTEK RESOLVE
============================================================

Agentes de IA podem analisar dados, planejar, usar ferramentas e executar tarefas.

O problema aparece quando esses agentes passam a:

- gastar dinheiro;
- contratar serviços;
- comprar produtos;
- usar APIs pagas;
- consumir cloud;
- negociar com fornecedores;
- acessar sistemas;
- tomar ações com impacto financeiro.

Uma empresa não pode simplesmente entregar um cartão, uma conta ou credenciais ilimitadas para um agente.

É necessário controlar:

- quem é o agente;
- qual é seu objetivo;
- quanto pode gastar;
- onde pode gastar;
- com quem pode transacionar;
- qual categoria é permitida;
- quando precisa de aprovação;
- quais sistemas pode acessar;
- qual foi o motivo da ação;
- qual foi o resultado;
- quem autorizou;
- o que aconteceu depois.

A Voytek é a camada que fornece esse controle.

============================================================
4. PRINCÍPIO MAIS IMPORTANTE DO SISTEMA
============================================================

O LLM NÃO É A AUTORIDADE FINANCEIRA FINAL.

O fluxo conceitual é:

AGENTE/LLM
    ->
PROPÕE UMA AÇÃO
    ->
VOYTEK RECEBE A SOLICITAÇÃO
    ->
POLICY ENGINE
    ->
ALLOW / DENY / HUMAN_APPROVAL
    ->
EXECUÇÃO OU SIMULAÇÃO
    ->
LEDGER
    ->
OUTCOME
    ->
AUDIT

O LLM pode:

- interpretar contexto;
- analisar informações;
- comparar alternativas;
- planejar;
- explicar;
- estruturar uma intenção;
- sugerir uma ação;
- selecionar uma ferramenta permitida.

O LLM não pode sozinho:

- autorizar uma despesa;
- ignorar um budget;
- ignorar uma policy;
- alterar seu próprio nível de autonomia;
- aprovar sua própria solicitação;
- ignorar um DENY;
- executar uma operação sensível sem passar pelo Policy Engine.

============================================================
6. USUÁRIOS, EMPRESAS E MULTI-TENANCY
============================================================

A Voytek é SaaS multi-tenant.

Cada empresa é um Tenant.

Dados de uma empresa nunca podem ser acessados por outra empresa.

Entidades relevantes devem possuir TenantId quando aplicável.

Papéis iniciais:

OWNER
- proprietário da organização;
- maior nível administrativo.

ADMIN
- administra usuários, agentes, policies e configurações.

MANAGER
- gerencia operações, objetivos, budgets e approvals permitidos.

OPERATOR
- acompanha e opera fluxos permitidos.

VIEWER
- acesso somente de leitura às informações autorizadas.

O backend deve sempre validar tenant e autorização.

O frontend nunca é a única barreira de segurança.

- consultar agente;
- listar agentes;

- suspender agente;

============================================================
9. OBJECTIVES
============================================================

Um Objective representa o resultado que o agente deve buscar.

Exemplos:

"Reduzir o custo de cloud em 15%."

"Manter estoque de EPI suficiente para 100 funcionários."

"Gerenciar até R$ 5.000 por mês em ferramentas de marketing."

"Reduzir assinaturas SaaS ociosas."

Campos conceituais:

- Id;
- TenantId;
- AgentId;
- Name;
- Description;
- Status;
- StartDate;
- EndDate opcional;
- métricas/resultado esperado quando aplicável.

Um gasto ou ação deve poder ser associado ao Objective que o justifica.

============================================================
10. BUDGETS E SUBACCOUNTS
============================================================

Budget é o orçamento lógico disponível para um agente ou objetivo.

No MVP, NÃO representa dinheiro custodiado pela Voytek.

Estados/valores importantes:

TOTAL
RESERVED
SPENT
AVAILABLE

Conceito:

AVAILABLE = TOTAL - RESERVED - SPENT

Fluxo típico:

AVAILABLE
    ->
RESERVED
    ->
EXECUTED

ou:

AVAILABLE
    ->
RESERVED
    ->
RELEASED

Reserva é importante para evitar que duas operações simultâneas gastem o mesmo saldo.

Valores monetários:

NUNCA usar float ou double.

Usar decimal no C# e numeric/decimal no PostgreSQL.

Subaccounts/sub-budgets permitem separar orçamento por:

- agente;
- objetivo;
- categoria;
- finalidade.

Exemplo:

Budget total da empresa: R$ 30.000.

Marketing Agent: R$ 5.000.
EPI Agent: R$ 8.000.
SaaS Agent: R$ 3.000.
IT/Cloud Agent: R$ 4.000.
Procurement: R$ 10.000.

============================================================
11. NÍVEIS DE AUTONOMIA
============================================================

A Voytek deve possuir inicialmente três níveis:

MANUAL

O agente:
- analisa;
- recomenda;
- cria proposta;
- não executa ação sensível sozinho.

SUPERVISED

O agente:
- pode executar ações dentro de limites;
- exceções ou operações acima de determinados limites exigem humano.

AUTONOMOUS

O agente:
- possui maior autonomia operacional;
- ainda continua sujeito a budgets, policies, segurança e Kill Switch.

IMPORTANTE:

AUTONOMOUS NÃO significa "sem regras".

Nenhum nível de autonomia pode ignorar o Policy Engine.

============================================================
12. POLICY ENGINE / FINANCIAL FIREWALL
============================================================

Este é um dos componentes centrais da Voytek.

Toda ação sensível deve passar pelo Policy Engine.

Entrada conceitual:

AuthorizationRequest.

Pode conter:

- TenantId;
- AgentId;
- ObjectiveId;
- BudgetId;
- ActionType;
- Amount;
- Currency;
- Supplier/Merchant;
- Category;
- Purpose;
- timestamp;
- contexto adicional;
- idempotency key;
- correlation id.

O motor pode verificar:

- agente está ativo?;
- budget existe?;
- budget possui saldo?;
- valor está dentro do limite?;
- fornecedor é permitido?;
- categoria é permitida?;
- horário é permitido?;
- objetivo está ativo?;
- finalidade corresponde ao objetivo?;
- nível de autonomia permite?;
- existe regra que exige humano?;
- existe regra que bloqueia?;
- Kill Switch está ativo?;
- operação já foi processada?

Saídas obrigatórias:

ALLOW
DENY
HUMAN_APPROVAL

Toda decisão deve registrar o motivo.

Exemplo:

ALLOW
Reason:
"Valor R$ 180 abaixo do limite automático de R$ 500; fornecedor autorizado; budget disponível."

DENY
Reason:
"Fornecedor não permitido pela policy POL-019."

HUMAN_APPROVAL
Reason:
"Valor R$ 2.500 excede limite automático de R$ 2.000."

============================================================
13. INTENT-TO-PAY / OBJECTIVE-BASED MONEY
============================================================

Conceito importante da Voytek:

não verificar somente "quanto" e "onde".

Também verificar "por quê".

Uma ação pode carregar Purpose/Intent.

Exemplo:

Objective:
"Reduzir custo de cloud."

Proposta:
"Comprar 20 camisetas."

Mesmo que exista saldo, a ação não corresponde ao objetivo.

O sistema pode utilizar IA para interpretar contexto ou finalidade quando necessário.

Entretanto:

a IA fornece classificação/contexto.

A decisão final continua sendo aplicada pelo Policy Engine.

============================================================
14. SMART APPROVALS
============================================================

Quando uma operação retorna HUMAN_APPROVAL:

o sistema cria uma ApprovalRequest.

Ela deve conter:

- agente;
- objetivo;
- ação;
- valor;
- fornecedor;
- motivo;
- policy responsável pelo escalonamento;
- contexto necessário;
- status;
- solicitante;
- aprovador;
- timestamps.

Estados possíveis:

PENDING
APPROVED
REJECTED
EXPIRED
CANCELLED

O usuário autorizado pode:

- aprovar;
- rejeitar;
- consultar detalhes.

Uma aprovação deve ser idempotente.

Não permitir aprovação dupla.

O objetivo de Smart Approvals é evitar mandar tudo para humano.

Apenas exceções ou operações que realmente precisam de decisão humana devem ser escaladas.

============================================================
15. KILL SWITCH
============================================================

Deve existir uma forma de suspender rapidamente um agente.

Ao ativar o Kill Switch:

- novas autorizações devem ser bloqueadas;
- novas ações sensíveis devem parar;
- o evento deve ser auditado.

O Kill Switch deve ser validado no backend.

============================================================
16. SHADOW MODE
============================================================

Shadow Mode é uma funcionalidade central do MVP.

Objetivo:

permitir que a empresa teste um agente antes de liberar ações reais.

O agente continua:

- recebendo objetivo;
- analisando contexto;
- criando propostas;
- passando pelo Policy Engine;
- recebendo ALLOW/DENY/HUMAN_APPROVAL.

Mas nenhuma ação financeira/externa real é executada.

O sistema registra:

- o que o agente faria;
- quanto gastaria;
- onde gastaria;
- quais policies foram acionadas;
- o que seria permitido;
- o que seria negado;
- o que exigiria humano;
- resultado estimado quando disponível.

IMPORTANTE:

Shadow Mode deve usar o mesmo pipeline de autorização da operação real.

A diferença deve estar na execução.

Real executor -> não chamado.

Simulation executor -> chamado.

============================================================
17. LEDGER
============================================================

O Ledger registra os movimentos econômicos relevantes.

Ele deve ser append-only.

Não alterar silenciosamente um registro financeiro histórico.

Correções devem usar novos lançamentos/compensações.

Eventos possíveis:

BUDGET_ALLOCATED
BUDGET_RESERVED
BUDGET_RELEASED
EXPENSE_AUTHORIZED
EXPENSE_DENIED
EXPENSE_EXECUTED
ADJUSTMENT

Cada registro deve poder carregar:

- TenantId;
- AgentId;
- ObjectiveId;
- BudgetId;
- AuthorizationId;
- Amount;
- Currency;
- Type;
- Timestamp;
- CorrelationId;
- metadata.

============================================================
18. AUDIT LOG
============================================================

Audit Log registra ações administrativas e de segurança.

Exemplos:

- usuário criou agente;
- usuário mudou autonomia;
- policy foi criada;
- policy foi alterada;
- budget foi modificado;
- agente foi suspenso;
- approval foi aprovado;
- approval foi rejeitado;
- API key foi criada/revogada;
- Kill Switch foi acionado.

Audit Log deve permitir responder:

Quem fez?
O quê?
Quando?
Em qual tenant?
Em qual recurso?
Qual era o correlation id?
Qual foi o resultado?

============================================================
19. OUTCOME LEDGER
============================================================

A Voytek não deve medir somente quanto o agente gastou.

Também deve medir o resultado.

Exemplo:

Marketing Agent:

Gasto:
R$ 2.000.

Resultado:
93 leads.

CPL:
R$ 21,50.

Outro exemplo:

EPI Agent:

Compra:
R$ 5.200.

Resultado:
estoque normalizado para 30 dias.

Economia:
R$ 430 em relação à cotação anterior.

Outcome pode conter:

- AgentId;
- ObjectiveId;
- Transaction/AuthorizationId;
- Metric;
- Value;
- Unit;
- Description;
- Timestamp.

O Outcome Ledger é importante para futuramente avaliar:

- eficiência;
- ROI;
- confiança;
- autonomia;
- performance dos agentes.

============================================================
21. AI ORCHESTRATOR
============================================================

A Voytek pode ter seus próprios agentes e também receber solicitações de agentes externos.

O AI Orchestrator organiza o uso do LLM.

Deve existir abstração:

ILLMProvider

Objetivo:

não acoplar todo o produto a um único fornecedor/modelo.

Responsabilidades:

- montar contexto mínimo necessário;
- chamar o LLM;
- solicitar structured output;
- validar formato;
- controlar tools;
- registrar tokens/custo/latência;
- aplicar timeout;
- lidar com falha;
- devolver proposta estruturada para a aplicação.

Estratégia de custo:

NÃO usar LLM quando uma regra determinística resolve.

Exemplo:

R$ 180.
Fornecedor permitido.
Budget disponível.
Limite automático R$ 500.

Isso deve ser resolvido em C#.

Custo de LLM:
ZERO.

LLM deve ser usado quando for necessário:

- interpretar texto;
- entender intenção;
- comparar alternativas;
- analisar informações não estruturadas;
- planejar;
- transformar resultado em ação estruturada.

Modelo econômico padrão planejado:

GPT-5.6 Luna Low ou modelo equivalente econômico/rápido.

Casos complexos podem futuramente ser roteados para modelos mais capazes.

O sistema deve monitorar:

- input tokens;
- output tokens;
- custo;
- latência;
- provider;
- model;
- tenant;
- agent.

============================================================
27. IDEMPOTÊNCIA
============================================================

Operações sensíveis não podem acontecer duas vezes por acidente.

Exemplos:

- reservar budget;
- executar ação;
- criar movimento financeiro;
- processar webhook futuro;
- concluir commerce;
- aprovar request.

Usar Idempotency-Key quando adequado.

Retry de rede nunca pode duplicar uma operação.

============================================================
28. CONCORRÊNCIA DE BUDGET
============================================================

Cenário:

Budget disponível:
R$ 1.000.

Dois agentes/processos tentam reservar R$ 800 ao mesmo tempo.

O sistema não pode permitir R$ 1.600.

A reserva precisa ser transacional.

Pode usar:

- transaction;
- optimistic concurrency;
- row locking quando necessário;
- constraints.

Consistência financeira é mais importante que conveniência.

Quando a escala justificar, eventos assíncronos podem migrar para broker externo.

============================================================
30. SEGURANÇA
============================================================

Princípios:

- least privilege;
- zero trust entre ações sensíveis;
- tenant isolation;
- server-side authorization;
- secrets fora do código;
- HTTPS;
- rate limiting;
- validação de input;
- logs sem secrets;
- auditabilidade;
- tokens com escopo;
- expiração/revogação de credentials;
- proteção contra replay quando aplicável.

Nunca colocar em prompt de LLM:

- senhas;
- API keys desnecessárias;
- tokens brutos desnecessários;
- secrets.

O agente deve receber apenas o contexto necessário.

35. EXEMPLO COMPLETO DE FLUXO
============================================================

Cenário:

EPI Agent percebe que o estoque de luvas está abaixo do mínimo.

Objective:

"Manter estoque de EPI suficiente para 100 funcionários."

Budget mensal:

R$ 8.000.

Disponível:

R$ 5.300.

Proposta:

Comprar R$ 1.450 em luvas do fornecedor ABC.

Fluxo:

1. Agente identifica a necessidade.

2. LLM, se necessário, transforma contexto em proposta estruturada.

3. Aplicação valida formato e identidade.

4. AuthorizationRequest é criada.

5. Policy Engine verifica:
   - agente ativo;
   - objective ativo;
   - budget disponível;
   - fornecedor permitido;
   - categoria EPI;
   - valor;
   - autonomia;
   - policies;
   - Kill Switch.

6. Resultado:

ALLOW.

7. Budget pode reservar R$ 1.450.

8. Se Shadow Mode estiver ativo:
   - nenhuma compra real acontece;
   - sistema registra "would execute";
   - ledger/simulação registra o cenário.

9. Se execução real existir no futuro:
   - executor autorizado realiza ação;
   - operação é confirmada;
   - reserva vira gasto.

10. Ledger registra.

11. Audit registra eventos relevantes.

12. Outcome posteriormente pode registrar:

"Estoque normalizado para 30 dias."

36. DEFINIÇÃO DE MVP CONCLUÍDO
============================================================

O MVP está funcional quando uma empresa consegue:

1. criar conta;
2. criar organização;
3. adicionar usuários;
4. criar agente;
5. definir autonomia;
6. criar objetivo;
7. atribuir budget;
8. criar policies;
9. enviar AuthorizationRequest;
10. receber ALLOW/DENY/HUMAN_APPROVAL;
11. aprovar/rejeitar quando necessário;
12. testar agente em Shadow Mode;
13. consultar Ledger;
14. consultar Audit;
15. registrar Outcome;
16. testar Commerce lógico entre agentes;
17. usar AI Orchestrator para propostas;
18. acompanhar tudo pelo dashboard;
19. integrar agente/sistema pela API;
20. suspender agente pelo Kill Switch.

Tudo isso deve funcionar sem a Voytek precisar custodiar dinheiro real.

14. Existe forma mais simples e determinística de resolver sem LLM?
